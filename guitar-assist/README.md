# 无障碍吉他助手 (guitar-assist)

面向视障 / 低视力用户的**吉他调音 + 和弦辅助**嵌入式应用，
目标平台 **泰山派 RK3566**（Cortex-A55 ×4 @1.8GHz，带 NPU）。

---

## 这个项目解决什么问题

普通调音器靠"看指针"，视障用户用不了。本项目把调音和和弦信息
**编码到听觉和触觉通道**，做到闭眼也能把吉他调准、也能查和弦指法。

| 功能 | 实现方式 | 状态 |
|---|---|---|
| 六弦标准调音 | YIN 基频检测，精度 < 0.15 音分 | 已完成并验证 |
| 降弦/变调支持 | 支持到 65Hz（C 调弦） | 已完成并验证 |
| 听觉反馈 | 方向编码提示音 + 参考音播放 | 已完成 |
| 振动反馈 | 偏差强度编码 | 已完成 |
| 语音播报 | 和弦指法转中文语音文本 | 已完成 |
| 和弦指法库 | 28 个常用和弦，含语音描述 | 已完成并验证 |
| 实时和弦识别 | 色度图 + 模板匹配，11/11 通过 | 已完成并验证 |
| 和弦识别 NPU 加速 | RKNN + CNN（可选增强） | 代码就绪，待训练 |

## 快速开始

### PC 上先跑（强烈建议）

所有算法都应该**先在 PC 上验证**，因为 PC 上能 printf/gdb/valgrind，
而板子上只能看串口日志。

```bash
git clone <repo> && cd guitar-assist
sudo apt install libasound2-dev cmake build-essential
./scripts/build-pc.sh
```

脚本会自动构建并跑一遍自测。然后：

```bash
cd build-pc
./test_yin                      # 调音算法精度测试 (19 项)
./test_chord                    # 和弦库校验 (28 个和弦)
./test_chroma                   # 色度图特征验证
./test_recog                    # 和弦识别端到端 (11 项)
ctest                           # 一次跑完全部

./guitar_assist chords          # 列出所有和弦指法
./guitar_assist file x.wav      # 离线分析一段录音
./guitar_assist tuner hw:1,0    # 实时调音
./dev_scan                      # 扫描可用音频设备
```

### 交叉编译到 RK3566

```bash
sudo apt install gcc-aarch64-linux-gnu

# 用泰山派 SDK 的 sysroot 最省事（推荐）
export SYSROOT=/path/to/tspi-sdk/sysroot
./scripts/build-rk3566.sh

# 或者手动指定 ALSA 路径
export ALSA_INC=/path/to/alsa/include
export ALSA_LIB=/path/to/alsa/lib/libasound.so
./scripts/build-rk3566.sh
```

部署：

```bash
scp build-rk3566/{guitar_assist,dev_scan,tuner_demo} root@<板子IP>:/root/guitar/
ssh root@<板子IP>
cd /root/guitar
./dev_scan                    # 先确定设备号
./guitar_assist both hw:1,0   # 启动
```

运维细节见 [`docs/DEPLOY.md`](docs/DEPLOY.md)。

> **代码在云端，怎么拿到本地？**
> 见 [`docs/GET-LOCAL.md`](docs/GET-LOCAL.md) —— 三种方式任选
> （git bundle / zip / GitHub），含验证步骤和常见问题。

## 核心设计决策

### 1. 为什么用 YIN 而不是自相关（ACF）

吉他的谐波结构特殊——**基频常常弱于二次谐波**。
朴素的 ACF 在这种情况下八度误判率很高（弹低音 E 会报成 E3）。
YIN 通过 CMNDF（累积均值归一化差函数）抑制了这个问题。

实测：把二次谐波做到基频的 2.2 倍强度后，YIN 依然准确，
六根弦误差全部 < 0.15 音分。

### 2. 为什么低音弦在色度图里被"丢弃"

4096 点 FFT 在 44.1kHz 下 bin 宽 ≈ 10.8Hz。
低音 E（82.41Hz）处相邻半音的频率差只有 **4.9Hz** ——
一个 bin 就跨了两个半音，算出的 pitch class 是错的。

所以 `chroma.c` 里从 **140Hz** 开始才映射到音级。
低音弦的信息由 YIN 单音检测补足。这是**明确的取舍**，不是 bug。

### 3. 和弦识别的"包含关系裁决"

模板匹配有个固有陷阱：`Cmaj7 = C-E-G-B` 完全包含 `C = C-E-G`。
弹 C 时，如果录音里 B 有一点能量（泛音/串音），
Cmaj7 的得分会**反过来压过真正的 C**。

解决办法：当候选是扩展和弦时，检查它"多出来的那个音"是否
有足够证据（能量占比 > 0.12）。证据不足就退回简单三和弦。

引入这个裁决后，识别率从 5/11 提升到 **11/11**。

### 4. 无障碍反馈的三通道设计

| 通道 | 偏低的编码 | 偏高的编码 | 准了的编码 |
|---|---|---|---|
| 提示音 | 380Hz 低音 | 880Hz 高音 | 上升三音 C5-E5-G5 |
| 节拍 | 慢（2.5Hz） | 快（4Hz） | — |
| 振动 | 长振 | 长振 | 双击 |
| 语音 | "偏低，请紧弦" | "偏高，请松弦" | "准了" |

**关键原则：三个通道的"梯度方向"必须一致**——越接近目标，
提示越缓和。这样用户本能就知道往哪调，不需要学。

振动不编码方向（振动很难表达高低），只编码"还差多少"。

## 实测数据

### 调音精度（test_yin，19/19 通过）

| 弦 | 目标频率 | 实测 | 误差 |
|---|---|---|---|
| 6弦 低音E | 82.41 Hz | 82.41 Hz | +0.11 音分 |
| 5弦 A | 110.00 Hz | 110.00 Hz | −0.02 音分 |
| 4弦 D | 146.83 Hz | 146.83 Hz | +0.01 音分 |
| 3弦 G | 196.00 Hz | 196.00 Hz | −0.02 音分 |
| 2弦 B | 246.94 Hz | 246.95 Hz | +0.03 音分 |
| 1弦 高音E | 329.63 Hz | 329.63 Hz | +0.03 音分 |

降弦场景（Drop D 73.42Hz、C 调弦 65.41Hz）同样准确。
静音/白噪声正确拒识。

### 和弦识别（test_recog，11/11 通过）

10 个和弦全部正确识别（含 C/Cmaj7 边界情况），静音拒识通过。
匹配分数区间 0.706~0.785，判定阈值 0.70。

### 性能预算（RK3566 A55 @1.8GHz）

| 环节 | 耗时 |
|---|---|
| 音频采集一帧 | 93 ms（节奏，非计算） |
| YIN 基频检测 | < 1 ms |
| 色度图提取（4096 点 FFT） | ~1.5 ms |
| 模板匹配（72 次） | ~0.2 ms |
| RKNN 推理（15K 参数） | ~3 ms（可选） |

**计算总耗时 < 5ms，相对 93ms 的帧间隔余量充足。**
瓶颈永远在音频采集质量，不在算力。

## 屏幕界面

目标屏是 **1.54 寸 IPS / ST7789 / SPI / 240×240**。界面层**没有用 LVGL**，
而是自己写了约 600 行绘图原语 —— 原因很实际：

- LVGL 是几十万行的库，编译进项目要十几分钟，配置项几十个；
- 我们只需要画大字、矩形条、圆点、格栅这几种固定元素；
- 自绘让屏在**接上线的那一刻**就能亮，可以直接验证硬件，
  不用先花一天折腾 LVGL 编译。

如果以后要滑动列表/动画/多页面，再引入 LVGL 也不迟 ——
`display_drv` 那一层已经按 LVGL 的 `flush_cb` 接口形状设计好了。

### 三个页面

| 页面 | 内容 |
|---|---|
| **调音** | 音名超大字（32px）+ 频率 + 第几弦 + 音分偏差指针条 |
| **和弦** | 和弦名大字 + 中文名 + 置信度进度条 + 实时指法图 |
| **指法** | 和弦库浏览，左右箭头翻页，指法图 + 品位数字 |

### 无障碍设计要点

1. **颜色不是唯一信息载体** —— "偏低"同时有红色 + 文字 + 指针偏左，
   色盲用户靠文字和位置也能读懂；
2. **字号尽量大** —— 主音名 32px，占屏高 13%；
3. **高对比** —— 纯黑底 + 高亮前景，不用灰色调（户外光下灰底看不清）；
4. **状态用"动词 + 数值"** —— 显示"偏低了，请调紧"而不是纯符号。

# 转成 PNG 看

### 点阵字库

汉字不做全字库（全字库几 MB），只把界面用到的**132 个字**提取出来，
5 套字库合计约 **100 KB**：

| 字库 | 字号 | 用途 | 符号前缀 |
|---|---|---|---|
| `font_num10.h` | 10px ASCII | 频率、置信度、品位数字 | `f10_` |
| `font_num16.h` | 16px ASCII | 和弦名、状态小字 | `f16_` |
| `font_num32.h` | 32px ASCII | 主音名大字 | `f32_` |
| `font_cn12.h` | 12px 汉字 | 小号中文标签 | `cn12_` |
| `font_cn16.h` | 16px 汉字 | 常用中文 | `cn16_` |

要加新汉字：改 `tools/gen_font.py` 里的 `DEFAULT_CHARS`，
然后跑 `bash scripts/gen-fonts.sh` 重新生成。

> **踩过的坑**：5 个头文件最初共用同一个包含保护宏 `GA_FONT_GEN_H`，
> 导致 include 多个字库时**只有第一个生效**（后面全被 `#ifndef` 挡掉），
> 症状是"用了别的字号却报符号未定义"。修法是让保护宏带前缀
> （`GA_FONT_CN16_H`），同时符号名也带前缀（`cn16_blob` / `cn16_table`）。

### 点亮屏幕

`docs/LCD-SETUP.md` 是完整的点亮手册，`dts/st7789-tspi.dtsi` 是设备树配置。
核心事实：

- 泰山派 SPI3 控制器地址 `fe640000`，pinctrl 有 M0/M1 两组复用；
- ST7789 是 IPS 屏，**必须发反色命令**（`0x21`），否则颜色全反；
- SPI 屏带宽是瓶颈：全屏 115 KB，40 MHz 下约 30~50 ms/帧，
  所以界面用**脏矩形局部刷新**，只刷变化的那一块。

**⚠️ 设备树方案需要重编译内核**，且沙箱里没有 aarch64 工具链，
所以设备树和交叉编译脚本**都没有实测过**，需要你在本地验证。

## 已知限制

诚实记录，避免误导：

1. **合成测试 ≠ 真实录音**。当前所有测试用合成信号。
   真实吉他（混响、按弦噪声、和弦外音）准确率会下降。
   **下一步应该用真实录音重跑测试。**

2. **低音弦色度图信息缺失**。这是 FFT 分辨率的物理限制，
   导致 `Am` 和 `A` 这类"只差低音弦"的和弦对容易混淆。
   缓解方案需要结合单音检测。

3. **高把位 / 大横按和弦未充分测试**。当前和弦库以开放把位为主。

4. **RNNN 路径未完成训练**。代码框架和转换脚本就绪，
   但模型需要真实数据训练。当前跑的是模板匹配后端的实现。

5. **振动硬件依赖具体板子**。默认走 LED 子系统路径，
   泰山派上如果有 PWM 振动马达需要改路径。
