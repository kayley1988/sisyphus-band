# 开发过程中的实测发现

这份文档记录**开发时真正踩到的坑和实测结果**，不是理论推导。
目的是让后来者（包括几个月后的自己）不重蹈覆辙。

---

## 1. 调音时应该取"拨弦后 0.3~1 秒"的稳定段

**现象**：对合成的六弦音频做分析时发现，每根弦**起音瞬间**测量最准
（误差 ±0.3 音分），到 0.75 秒后偏差增大到 +15.7 音分。

```
t=0.00s   82.39 Hz E2  (-0.3 音分)   准
t=0.25s   82.41 Hz E2  (+0.1 音分)   准
t=0.50s   82.45 Hz E2  (+1.0 音分)   准
t=0.75s   83.16 Hz E2  (+15.7 音分)  偏高 ← 尾音阶段
```

**原因**：真实吉他弦的高次谐波衰减比基频快。尾音阶段谐波结构
改变，基频相对变强，YIN 的估计会轻微漂移。

**结论**：
- 调音时应取**拨弦后 0.3~1 秒**的稳定段，不要等声音快没了再测
- 产品交互上应该引导用户"拨响弦，让它响一会儿"，而不是拨一下就松手
- 这不是 bug，是物理现象。**任何**基频检测算法都会有这个表现

## 2. 色度图丢弃低音弦是必须的，不是可选优化

**验证方法**：打印 4096 点 FFT 的 bin 宽度对比半音间隔。

```
4096 点 @ 44100Hz → bin 宽 = 10.8 Hz

音符     频率      相邻半音间隔    够不够
6弦 E2   82.41 Hz   4.9 Hz        不够（一个 bin 跨 2 个半音）
5弦 A2  110.00 Hz   6.5 Hz        不够
4弦 D3  146.83 Hz   8.7 Hz        勉强
3弦 G3  196.00 Hz  11.6 Hz        够了
```

**结论**：
- 低于 140Hz 的 bin 必须丢弃，否则 pitch class 是随机噪声
- 想保留低音弦信息只能：① 用更长 FFT（8192 点，代价是延迟翻倍）
  或 ② 对低频段做对数频率重采样（需要重采样滤波器，工程量大）
- 当前选择丢弃，靠 YIN 单音检测补足

## 3. Cmaj7 会在模板匹配里"吃掉" C

**现象**：端到端测试第一版只通过 5/11。
`C` 被识别成 `Cmaj7`，`F` 被识别成 `Fmaj7`，`G`/`Em`/`D`/`E` 完全识别不出。

**原因 1 — 包含关系**：
`Cmaj7 = C-E-G-B` 完全包含 `C = C-E-G`。
当录音里 B 有一点能量（泛音、相邻弦串音），
Cmaj7 因为"多余音惩罚更低"反而得分更高。

**原因 2 — 编码解码不对称（真 bug）**：
```c
// 错误版本
encode: (int)q % 6          // q 是 1~6，1%6 = 1
decode: (key % 6) + 1       // 解出 2 → MINOR
// 结果: C(MAJOR, q=1) 解出 MINOR，整体错位
```
修正为 `(q - 1)` / `(key % 6 + 1)` 后修复。

**解决**：引入"额外音证据门槛"。扩展和弦的额外音能量必须
> 0.12 才算数，否则退回简单三和弦。

**依据**（来自实际测量）：
```
真实和弦音能量占比：0.17 ~ 0.28
泛音制造的杂音占比：0.04 ~ 0.09
→ 门槛放 0.12，正好卡在中间
```

**效果**：5/11 → 8/11 → **11/11**

**教训**：这个 bug 只有靠端到端测试才能发现。
`test_chroma` 里特征提取是对的（top3 音级 100% 正确），
问题全在决策层。**分层测试 + 端到端测试缺一不可。**

## 4. 单音不会误报为和弦（好消息）

**验证**：用六根弦依次弹响的音频（全是单音）跑 `guitar_assist file`。

```
t=  0.00s  音高   82.39 Hz E2   [6弦 低音E]
t=  1.00s  音高  109.99 Hz A2   [5弦 A]
...
---------------- 汇总 ----------------
分析窗口: 12, 有效音高: 12, 识别到和弦: 0   ← 正确！
```

**结论**：色度图对于单音只会有一个峰，与三音模板的余弦相似度
天然较低（约 0.5~0.6），低于 0.70 阈值，所以不会误报。
这个阈值选得合适。

## 5. ALSA 头文件和 `-std=c11` 冲突

**现象**：
```
/usr/include/alsa/global.h:144: error: redefinition of 'struct timespec'
```

**原因**：`-std=c11` 会关闭 `_POSIX_C_SOURCE` 等特性宏，
而 ALSA 的头文件依赖 POSIX 扩展，自己定义了 `struct timespec`，
与 glibc 的冲突。

**解决**：用 `-std=gnu11` 而不是 `-std=c11`。

CMake 里对应：
```cmake
set(CMAKE_C_STANDARD 11)
set(CMAKE_C_EXTENSIONS ON)    # ← 关键，打开 GNU 扩展
```

## 6. 静态库的链接依赖必须用 PUBLIC 传递

**现象**：`test_feedback` 链接时报一堆 `undefined reference to snd_pcm_*`。

**原因**：`ga_feedback` 在 `GA_HAVE_ALSA` 下会调用 ALSA 函数，
但 CMake 里只写了 `target_compile_definitions(... PUBLIC GA_HAVE_ALSA)`
（这只影响宏定义可见性），没有把 **libasound 的链接依赖**传递出去。

**解决**：
```cmake
target_link_libraries(ga_feedback PUBLIC ${ASOUND_LIB})
```

**教训**：`target_compile_definitions` 和 `target_link_libraries`
是两回事。前者管"编译时看到什么宏"，后者管"链接时找什么库"。
静态库尤其容易踩这个坑，因为它自己不链接，等到最后才暴露。

## 7. 头文件注释里的 `*/` 会提前结束注释块

**现象**：`feedback.h` 编译报一堆莫名其妙的错：
```
error: unknown type name 'brightness'
error: stray '\343' in program
```

**原因**：注释里写了
```c
/* 振动: Linux 上走 /sys/class/leds/*/brightness 或 gpio, ... */
                                    ↑ 这个 */ 提前结束了注释！
```

**解决**：改写注释措辞，避免路径里出现 `*/`。

**教训**：写路径时特别注意 `*` 后面跟 `/` 的情况。
遇到"莫名奇妙"的编译错误，先检查最近的注释有没有提前闭合。

## 8. 提示音必须加淡入淡出

**问题**：直接截断的正弦波会有明显的"咔"声（pop）。

**原理**：信号的突然中断在频域上是宽带的，听起来就是"咔"。

**解决**：5ms 线性淡入淡出（`synth_tone` 里的 `fade`）。
对无障碍辅助设备尤其重要——这个咔声很干扰听觉反馈。

---

## 9. 反馈必须节流，否则没法用

**问题**：每 93ms 出一帧结果，如果每帧都触发提示音，
用户听到的是连续不断的"嘟嘟嘟嘟"，根本分辨不出节奏变化。

**解决**：
- 提示音最快 250ms（4Hz）
- 振动最快 500ms
- 参考音最快 1500ms
- 语音最快 800ms

**设计要点**：节流后**节奏本身携带信息**——
差得远时快（4Hz，有紧迫感），接近时慢（1.7Hz，暗示"快好了"）。

---

## 10. 测试用例的噪声要加够

**发现**：`test_yin` 里最初用 SNR ≈ 60dB 的噪声，所有算法都"完美"。
把噪声加到 SNR ≈ 30dB 后，才暴露出参数选择的敏感性。

**建议**：合成测试里至少加 3% 白噪声，并且测一遍纯噪声输入的拒识率。

另外，`test_chroma` 里在每帧叠加 ±200 的随机扰动测试鲁棒性，
这个强度是合适的（相当于轻微串音）。
