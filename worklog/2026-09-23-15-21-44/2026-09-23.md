## 双输入模式（按键 + 语音）实现（E:/pathfind_project/pathfind_main_pipeline.py）

Z 需求：学生学习场景（图书馆/课堂）不适合语音控制 → 做成**按键+语音两种可选输入模式**，默认按键模式。

**架构：统一命令路由（Cmd Enum + handle()）**
- 键盘/鼠标/语音三条输入源都只「产生命令」（Cmd 枚举 14 个），执行逻辑只有 main 里 handle() 一份
- 好处：加语音没分叉业务逻辑；以后加手势/串口/GUI 按钮只产命令不动执行层
- 键位新增：V 切输入模式；M 语音模式下轮换麦克风

**语音引擎：Vosk 离线 small-cn（E:/pathfind_android/vosk-model-small-cn，66MB）**
- vosk 包经阿里云源装上（清华源没有；代理反而挡路，直连 whl 也成功过）
- 词表匹配实测：TTS 合成 21 词 → Vosk 识别 20/21 命中（「按键模式」被听成「案件模式」→ 同音变体收进容错词表）
- 词表 44 条覆盖 13 命令，长词优先匹配，28/28 用例通过（含「关闭语音」不被「退出」抢词）
- VoiceListener：懒加载模型（preload 后台线程，按键模式零开销零录音）、partial 触发（响应快）、同命令冷却 1.2s、静音期重复 partial 去重、麦克风真正可释放

**踩坑实录**
1. 系统默认麦克风(index 1)是「能打开但无信号」的路由（播报时 RMS 反而 674→14），真正拾音的是 index 6「麦克风 (SPEAKER-J)」→ VOSK_MIC_INDEX=6 显式配置 + 打不开回退默认 + 失败时打印设备清单
2. index 6 也拾到过满幅白噪声（RMS 恒 17969，Vosk 全输出空）→ 扬声器回环测试法本身不可靠（远场+回环失真），最终判定：麦克风选择是设备问题，做成 UI 电平条（对数刻度 60–8000 RMS）+ M 键换设备让用户自己诊断，而不是 AI 猜
3. 疑似「并发加载 paddle+vosk 崩进程」复现为无冲突（vosk 0.7s 加载完，进程存活）；一次后台启动日志缺 [语音] 且进程 4m34s 后消失无 Traceback，前台重跑一切正常 → 判定偶发（疑似文件写入时序）

## Android 移植方案（09-28 答复 Z「刷安卓后代码怎么办」）

**分层结论**：已写代码**不用重写**（Python 标准库/threading/numpy 跨平台），要换来的是**运行时 + 平台绑定的三个模块**（显示层 cv2.imshow、抓屏 mss、输入 waitKey）。

**三条路线**
| 路线 | 做法 | 性能 | 工作量 | 适合 |
|---|---|---|---|---|
| **A. 安卓壳 + Python 内嵌**（推荐第一步） | Android Studio 空 Activity → Chaquopy(Gradle 插件装 CPython) 跑 Python + Kivy 画 UI；抓屏用 MediaProjection/MediaCodec | OCR 慢（Paddle-Lite~1-2s，RKNN 走 NNAPI 可到 100-300ms） | 1-2 周 | 快速验证、复用 pipeline |
| **B. Termux 直跑** | 装 Termux 直接跑 .py | 无 UI 集成 | 半天 | 临时验证 |
| **C. 全 Java/Kotlin 重写**（终极） | 显示层自绘、抓屏 MediaProjection、OCR 嵌 Paddle-Lite、翻译走 API | NPU 原生，最快 | 最贵 | 量产 |

**形态关键差异**：PC 版靠抓屏+置顶浮窗；安卓端**不需要抓屏**——A 用 MediaProjection（系统级录屏 API，1 个 base）/ B 直接拿到解码帧（我们自己的播放器或 ExoPlayer）→ 更干净。浮窗对应 **TYPE_APPLICATION_OVERLAY 系统悬浮窗**，但**安卓悬浮窗需要引导用户授权"显示在其他应用上层"**（白化病用户开一次即可）。

**已记录的推荐顺序**：先用 USB WiFi + Debian 把 pipeline 跑通（主线），安卓路线作为“预装软件/交付形态”验证，两者都不冲突（RK3588 可切镜像）。
