## 烧录脚本 v2 修复（用户实跑报错后）

## 烧录脚本 v3.1：修 `[Errno 9] Bad file descriptor`（写 16MB 后句柄作废）
- 用户实跑 v3 报错：选 Disk1（58.3GB USB）→ `Offline` → 打开成功 → `0% 4 MB (18.2 MB/s)` → `[FAILED] [Errno 9] Bad file descriptor`，`stopped after 16,777,216 bytes`（= 4 个 4MB 块）。
- 根因判断：Windows 上 ERROR_INVALID_HANDLE 映射为 errno 9。盘被 offline 后，第 1 个块改写了分区表 → Windows 重枚举设备 / 卷管理器介入 → **句柄被作废**，后续 write 全失败。所以「offline 释放卷锁」这招在 Windows 10/11 上反而有害。
- v3.1 四处改造（同一文件 `tools/flash_rdk_x5.py` 重写）：
  1. **写前 `diskpart clean`**（`online disk` + `attributes disk clear readonly` + `clean`）清掉所有卷 → 无卷锁、无可重枚举的卷；盘**保持 online**，不再 offline。
  2. **断点续写**：写循环捕获 OSError → 关句柄 → 按 RECOVERY 表轮换 6 种恢复动作（仅重开句柄 / offline / online / clean / 重开 / offline）→ 重新 diskpart → 重开设备 → `lseek` 回到本块起点 → 从镜像重新读该块重写。v3 是一失败就放弃，v3.1 最多救 6 次。
  3. 用 `os.open/os.lseek/os.write` 裸 fd（比文件对象更好处理重开）；短写按 `n - n%512` 推进保持扇区对齐。
  4. 写完**再封写前 4MB（MBR/分区表）**，即使中途触发过 clean 也不会留下无引导头的卡（clean 会抹 MBR，且 clean 发生在 offset>0 时置 `seal_needed`）。
- 恢复动作顺序刻意把「不抹 MBR」的排前面，只有第 4 次才用 clean。
- 校验：`python -W error py_compile` SYNTAX OK（nonlocal 绑定也在编译期校验过）。
- 新增 `刷机指南.md` 第八章「烧录脚本排错」表格（Errno 9 / 反复 retry / 死在同一偏移 / 打不开 / VERIFY MISMATCH 各自的处理）。
- 后续若还失败：换**机箱后置 USB 口**（优先 USB2）、换读卡器、或直接装 `tools/balenaEtcher-2.1.7.Setup.exe` 走 GUI。

## 全盘校验实跑：1 个坏块 @4MB+1000 —— 判定为 Windows FSInfo 改写（非坏卡）
- 结果：`FULL VERIFY FAILED - 1 bad block(s)`，块起点 4 MB，块内首差 +1000 B；389s / 19.6 MB/s；card sha 与 image sha 不同。
- 定位（用 Python 解析镜像 MBR + hexdump 验证）：镜像 `part1 type=0x0c(FAT32) lba=8192 = 4 MB`，`part2 type=0x83(ext4) lba=532480 = 260 MB`。差异绝对偏移 4,195,304 = 分区内 +1000；该处前 4 字节 `72 72 41 61` = FAT32 FSInfo 结构签名 `rrAa`（StrucSig 在 FSInfo+484），+1000 = **FSI_Free_Count（FSInfo+488）**。
- **判定：Windows 在镜像写到 4MB 后自动挂载了 FAT32 启动分区，改写了"空闲簇计数"。不是坏卡、不是写失败。**U-Boot/Linux 都不依赖 FSInfo，不影响启动。
- 修复方案（已落地）：
  1. `verify_rdk_x5.py` 新增 `repair()`：列出坏块后可输 `y` **就地补写**（automount disable → offline 卸载卷 → 开 RW 写 → 读回比对），秒级完成；新增 `image_partitions()` 解析镜像 MBR 和 `explain()` 自动判断差异落在哪个分区/是否 FSInfo 区并给出人话解释（已本地单测：正确输出"inside FAT32 partition 1 at +1000 B ... Harmless"）。
  2. `flash_rdk_x5.py` 写前加 `diskpart automount disable`（禁止 Windows 挂载新出现的卷）——这才是根治；写完**故意把盘留 OFFLINE**再 `automount enable` 恢复系统设置（盘 offline 就不会被挂载），用户直接拔卡。
  3. `diskpart()` helper 加 `num=None` 支持（automount 命令不能带 select disk）。
- 复用经验（重要）：**Windows 上给 SD 卡裸写含 FAT 分区的镜像，必须先 `automount disable`**，否则 Windows 一挂载就会改 FSInfo 空闲簇计数，导致全盘校验出现"假坏块"；同时也解释了之前 48MB 处的 write error——Windows 抢挂载并锁卷，靠 `clean` 清卷才解开。两个现象同源。
