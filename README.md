# 杭州罕见病黑客松 · 西西弗斯的乐队

> 一把**他自己能弹**的吉他。
>
> 给上肢功能受限的罕见病患者，做一套"机器补上他缺的那一分，但弹琴的人还是他自己"的自动压弦装置。

**杭州罕见病黑客松参赛项目** ｜ 面向肢体功能障碍用户的低成本、可复刻方案

---

## 一句话说清我们在做什么

这把吉他不是自动演奏机。

它不替任何人演奏 —— 它替人**做他做不到的那一个动作**（左手压弦），把右手和决定权完整地还给他。

系统的硬约束只有一条：

> **他不动，机器一个音都不响。**

## 站在谁的肩上：借鉴《拨云》

我们不遮掩这件事，主动写在这里。

本项目以开源项目 **《拨云》（boyun-guitar）** 为机械与上位机基础。拨云是一套成熟、完整、已在实物上跑通的自动演奏吉他：ESP32 + PCA9685 驱动 18 路舵机压弦/拨弦，RK3566 泰山派做上位机 —— 给它一份曲谱，它能把整首曲子完整弹出来。

**我们继承的部分：**

| 层级 | 来源 | 说明 |
|---|---|---|
| 机械结构 | 拨云开源 STL 件 | 齿条式压弦机构、拨弦机构、琴体夹持件，沿用并重新打印装配 |
| 上位机 | 拨云上位机代码 | 原生为泰山派 RK3566 编写并在该板上实测，同型号板可直接跑 |
| 串口帧协议 | 拨云协议 V3 | `AA 55 LEN TYPE PAYLOAD CRC16`，CRC16-CCITT，921600 bps |
| 舵机角度模型 | 拨云 `zero/base/offset` 体系 | `zero = 90` 为硬件真值，`base = zero + null_offset[ch]` |

**关于许可**：拨云的许可为 **CC BY-NC-SA 4.0 / PolyForm Noncommercial**。黑客松、研究、非商用完全无碍；商用需联系拨云原作者取得授权。本 README 即为致谢与出处声明。

## 为什么必须改造：我们换了一个问题

这是本项目存在的全部理由。同一副机械骨架，两个方向完全相反的问题：

| | 拨云 | 我们 |
|---|---|---|
| 问题 | 机器能不能把一首歌弹出来？ | 手不能弹的人，能不能**真的自己弹**？ |
| 设计前提 | **人不参与** | **人必须在场** |
| 系统性质 | 一台演奏机 | 一件义肢 |
| 成果衡量 | 机器弹得准不准 | **人弹得怎么样** |

拨云已经把第一个问题答完了，而且答得很好、全开源。但它的前提就是"人不参与" —— 整台机器是一台演奏机：给它谱，它弹完，结束。

我们要答的是第二个问题。这个问题在拨云里**一行代码都没有** —— 不是因为原作者没想到，而是因为**这个问题在原系统里根本不存在**。

> 义肢不做腿该做的事。它补上人缺的那一分能力，但走路的人还是人。
> 所以本系统的硬约束是：**他不动，机器一个音都不响。**

## 面向罕见病患者：我们改了什么

### 目标用户

上肢功能受限的罕见病患者 —— 包括神经系统罕见病、肌肉疾病、先天性肢体发育异常等，导致**手指无法独立、快速地完成和弦按压**的人群。

这类用户的痛点非常具体：

- **右手往往是好的** —— 拨弦、扫弦没问题，缺的只是左手
- **按不住和弦** —— 需要三指同时压弦、快速换把，这是最难补的一环
- **用不了看谱软件** —— 大量辅助工具依赖视觉界面，他们用不上
- **买不起专业辅具** —— 进口自适应乐器辅具动辄上万，且不适配亚洲人手型

所以我们的取舍很明确：**机器只接管"压弦"这一件事，其余全部还给人。**

### 四条核心改造

#### ① her 模式守护层 —— 把右手还给她，同时冒出三个新问题

拨云全自动模式下，音符之间舵机必然松开，所以下面这些问题**一个都不存在**。一旦把右手还给用户、让机器只在用户触发时压弦，三个问题同时出现：

| 新问题 | 对策 |
|---|---|
| 压弦无声，怎么提示"已就位" | 就位提示音 |
| 保持不动，舵机会烧 | 保持超时自动松弦 |
| 没有节拍锚点，不知道何时下手 | 预备拍倒计 |

这是本项目最有说服力的一点：**它证明了价值主张** —— 不是"我们没想到"，而是"这个问题在原系统里根本不存在"。

#### ② 和弦归约层 —— 从"识别得准"到"识别得能用"

《晴天》611 拍里有 **175 拍**是 6 个触摸方块按不了的"花和弦"。

对自动演奏机来说，"识别得准"是终点；对她来说，"**识别得准但按不出来，等于零**"。

所以本项目做归约：把按不出来的和弦，映射到她按得出来、并且听着还算对的那个。这是一个**无障碍项目才有的价值取向** —— 而它和原项目的目标函数是冲突的。

#### ③ 演奏档案 + 教练引擎 + 能力曲线 —— 把"她在演奏"变成可证明的数据

逐拍判定**早 / 准 / 晚 / 漏**，累积成命中率与能力曲线，长期归档到不开机也能翻看的档案室。

拨云不需要这个 —— 机器弹得准不准，看它自己就行。**只有"人在弹"的系统，才需要回答"人弹得怎么样"。**

这条需求是 her 模式独有的产物，也是本项目向康复训练场景迁移的接口。

#### ④ 导练层 + 小智板适配

- **导练层**：灯带只"导"不"代" —— 提示她该按哪里，但不替她按。全自动系统里不存在"导"这个概念。
- **小智板适配**：把拨云的 PCA9685 + 电流采样 + EEPROM 三件套，移植到小智 ESP32-S3；用 MAX471 把原作"电流法自动标定压弦深度"的链路救回来（零电流 0V 与拨云换算公式 `I = V/(shunt×gain)` 天然兼容）。

### 顺手修掉的拨云原版缺陷

| 缺陷 | 后果 |
|---|---|
| 上位机 `hardware.py` 缺 `import` | 整个程序起不来 |
| 触摸条 6 个引脚里 3 个不存在、1 个撞串口 | 触摸不可用 |
| 第一下拨弦是空动作 | 起手丢音 |
| `board_id=3` 落不进任何分支 | 电流显示从根上就是错的 |

## 系统架构

```
┌──────────────────────────────────────────────────────────┐
│  用户（右手拨弦 · 触摸选择 · 语音交互）                     │
└───────────────┬──────────────────────────────────────────┘
                │ 6 触摸条 / 4 物理按键 / 语音唤醒
┌───────────────▼──────────────────────────────────────────┐
│  泰山派 RK3566（上位机）                                   │
│  曲库解析 · 节拍时钟 · 和弦归约 · her 模式守护层           │
│  演奏档案 · 教练引擎 · 能力曲线 · TTS 语音播报             │
└───────────────┬──────────────────────────────────────────┘
                │ UART3 @921600 · 协议 V3
                │ AA 55 LEN TYPE PAYLOAD CRC16-CCITT
┌───────────────▼──────────────────────────────────────────┐
│  小智 ESP32-S3（下位机）                                   │
│  I2C → PCA9685 (0x40) · LEDC 直驱 · AIN0 ← MAX471          │
└───────────────┬──────────────────────────────────────────┘
                │ 18 路 PWM
┌───────────────▼──────────────────────────────────────────┐
│  12 路压弦舵机（齿条）· 6 路拨弦舵机                        │
│  MG996R · 24 个固定压点 · 6 段琴颈夹持                     │
└──────────────────────────────────────────────────────────┘
```

**关键约定（改之前请先读）：**

- **舵机角度**：`zero = 90`（硬件真值）；`base = zero + null_offset[ch]`；`angle = base + dir × press_offsets[弦][压深]`；拨弦钳位 `[55, 125]`
- **串口协议**：`AA 55 LEN TYPE PAYLOAD CRC16(大端)`，CRC16-CCITT（poly=0x1021, init=0xFFFF）覆盖 TYPE+PAYLOAD；`/dev/ttyS3` @921600，flock 排他
- **取整必须复刻 Python 的"五取偶" `round()`，不可用 `lround()`** —— 这个坑踩过一次，音符会整体偏移
- **引脚以 `obsidian笔记/无障碍吉他改造/48_接线总表_重接用.md` 为准** —— 不要按树莓派排布外推，也不要信引脚卡丝印（本项目在这上面翻过两次车）

### 先在 PC 上跑（强烈建议）

所有算法都应该先在 PC 上验证 —— PC 上能 `printf`/`gdb`/`valgrind`，板子上只能看串口日志。

```bash
cd guitar-assist
sudo apt install libasound2-dev cmake build-essential
./scripts/build-pc.sh
```

## 我们目前做不到的（主动承认）

**原理性限制：**

- **只覆盖 1–4 品**：齿条行程 = π × D × (转角 ÷ 360°)，舵机 ±90° 只能走 ±34 mm ≈ 2 个品位间距。要纯靠齿轮覆盖 12 品，齿轮直径需约 180 mm —— 工程上不可行。出路是滑轨位移或多串执行器，**不是加舵机数量**。
- **部分技巧做不到**：跨品滑音 / 连奏、推弦 / 揉弦、泛音、闷音 / 切音。根因相同 —— 本机构只有 **24 个固定压点、非连续位移**，而推弦/揉弦需要"弦张力连续变化"这个额外自由度，不是调参能补的。
- **速度天花板 BPM ≤ 120**：单音符最小间隔 100 ms（约 10 音/秒），这是 MG996R 的机械响应速度，不是软件问题。
- **表达力受曲库与触摸块封顶**：和弦库 50 个、触摸块 6 个。换把机构 v3 目前仍是空壳。

**工程风险：**

- 长时间保持压弦会烧舵机（her 模式天生的坑，全自动模式下音符之间必然松开，不存在此问题），现靠"保持超时自动松弦"兜底
- 压弦深度尚未在真琴逐弦标定，虚按与打品的边界目前只有估算值
- MAX471 量程 ±3 A、系统峰值 3.12 A，过流保护实际形同虚设，靠电源限流 + 保险丝兜
- 未做小时级老化测试（舵机温升、齿条磨损、夹持件松动）

**否定过的方案也记录在案**：我们复核过"变调夹方案"并证明它不成立（反而缩小可用音域）。否定一个方案也是研究结论。

## 可以迁移到哪些场景

1. **手功能康复训练器** —— her 模式的骨架与中风 / 手部损伤后的手功能训练同构：机器补上做不到的那一分、触发权完全在患者、系统记录进步曲线。"档案 → 教练 → 曲线"这条可测量的进步链，正是康复评估最缺的东西。
2. **盲文点显器 / 多点触觉显示** —— 本质与压弦同源："N 路独立执行器驱动一组触点"。24 压点机构、通道映射、逐点标定流程可直接复用。
